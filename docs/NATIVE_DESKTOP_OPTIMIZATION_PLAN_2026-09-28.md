# PDFMathTranslate 原生桌面迁移与资源优化实施方案

日期：2026-09-28

适用项目：`D:\paper\PDFMathTranslate-next`

用户已选路线：方案 1，WPF + .NET 10 LTS + WPF UI，保留 Python / BabelDOC 翻译能力。

本文用途：交给其他 AI 或开发者分阶段实施、测试、审核。**本文是实施规格，不代表功能或性能优化已经完成。**

## 0. 结论与执行边界

目标不是把 HTML 换成 XAML，而是同时完成四件事：

1. 原生桌面交互：移除默认桌面入口对 WinForms/WebView2/网页的依赖。
2. 降低空闲占用：空闲时不加载布局模型、不维持翻译 worker、不反复刷新整个任务列表。
3. 控制运行峰值：分开限制文档并行、本地计算线程、远程请求并发、预览缓存和模型驻留。
4. 精简可交付产品：从锁定依赖的洁净环境构建；安装体积、缓存、首次资源下载和运行内存分别核算。

默认决策：

| 项目 | 决策 |
|---|---|
| 原生 UI | WPF + .NET 10 LTS + WPF UI + CommunityToolkit.Mvvm |
| 开发起点 | 复用 WPF UI 的 MVVM 示例/模板及现有业务逻辑，不从零造控件库 |
| 进程关系 | WPF UI → 轻量 Python 控制进程 → 按任务启动的翻译 worker；预览另有按需的隔离渲染进程 |
| 通信 | 首期复用本机 HTTP API；补鉴权、健康检查、协议版本、SSE 增量事件 |
| 默认推理 | CPU；不因检测到独显就自动切换 GPU |
| 默认文档并行 | 1；批量导入可以排队，不等于同时运行多个大文档 |
| 发布 | 标准中文版 Inno Setup EXE，保留安装路径选择、卸载注册项及升级兼容 |
| 部署 | 首选自包含 .NET 多文件目录，由安装器封装；不强求应用本体为单文件 |
| 兼容回退 | 旧实现保留在源码/旧版本安装包，验收前不替换正式入口；不永久捆绑两套 UI |

不在首期范围：重写 Python 排版算法、引入本地大语言模型、Windows 服务常驻、跨平台、插件市场、自动 GPU 加速、复杂微服务、全功能 PDF 编辑器、差分更新。

资源优化不能以缺页、公式损坏、表格错位、禁用必要字体或改变翻译选项为代价。用户选择了单语/双语/术语表，就按选择生成；不能静默关闭功能来“跑出低占用”。

## 1. 当前项目的真实基线

### 1.1 已确认事实

以下路径相对仓库根目录；行号为本次检查时位置，修改后应以符号名定位。

| 现状 | 证据位置 | 对方案的影响 |
|---|---|---|
| 当前桌面是 .NET 8 WinForms + WebView2 | `launcher/PDFMathTranslateLauncher.csproj`、`launcher/MainForm.cs` | 原生迁移必须替换视图与交互，不只是 CSS 美化 |
| API 启动前同步预热 BabelDOC 资源 | `start-webui.py:92` 起；`BackendRunner.cs` 有 3 分钟就绪超时 | 窗口可用、API 可用、模型资源可用必须拆开 |
| 文档任务默认并行数为 2 | `source/pdf2zh_next/http_api.py:58` 起 | 双任务会叠加子进程、模型、PDF 中间数据 |
| 每个翻译任务已经有独立子进程，完成/取消后已有回收逻辑 | `source/pdf2zh_next/high_level.py:_translate_in_subprocess` | 先修补并复用隔离机制，不另套重复进程池 |
| Python 父进程在运行任务时导入 heavy high_level 模块 | `http_api.py:601`、`high_level.py:16` 起 | 子进程结束不代表父进程所导入的重型模块会释放 |
| 预览每次打开 PDF、生成 PNG，禁用缓存 | `http_api.py:_render_page_png`，约 110 行 | 翻页/切换会重复渲染；必须增加有界缓存与像素限制 |
| 历史限制 50 条只作用于写盘，不限制内存任务表 | `http_api.py:TaskRegistry._save/list` | 需要分页、终态淘汰策略；活动任务不能被淘汰 |
| 旧前端活动任务使用 1500 ms 轮询 | `webui/app.js:POLL_INTERVAL/pollTask` | 原生端统一事件源；空闲时不全量轮询 |
| 默认目标语言为 `zh`，不是必须手动选择才翻译 | `source/pdf2zh_next/config/model.py:TranslationSettings` | UI 显示明确的“英语 → 简体中文”等有效配置；不让默认值成为隐含行为 |
| 普通 QPS 默认 4，但免费服务配置会强制 QPS=20 | `config/model.py:433` 起；`translator/utils.py` 还会应用服务建议值 | 节能档必须约束最终生效值，不能只改设置界面 |
| 最大分块页数当前不允许小于 50 | `config/model.py:399` 起 | 10/20 页分块不是能直接开启的已有优化 |
| 工作目录、日志和配置目录解析不统一 | `http_api.py:WORK_DIR`、`start-webui.py:_resolve_home`、`launcher/Program.cs:LogPath/ConfigDirectory` | 装到 Program Files 时，不能把全部写入都假定可落在安装目录 |
| 安装器默认已经不含 Gradio 旧界面和重复 Python | `build/build-release.ps1` | 不能把已节省部分重复计入新方案收益 |

目前安装环境中的 BabelDOC metadata 版本为 **0.6.2**，依赖目录可能包含本地修补。实施前必须核对已安装文件与上游同版本 wheel 的差异，并归档补丁，不能仅依赖版本号判断二者相同。

额外引擎证据（相对 `uv-tools/pdf2zh-next/Lib/site-packages/babeldoc/`）：

- `docvision/doclayout.py:43` 起：Windows 实际只选择 CPUExecutionProvider；当前不走 CUDA/DirectML，没有显式设置 ONNX SessionOptions。
- 同文件先 `onnx.load()` 再 `SerializeToString()`，最后创建 ORT Session：是模型装载峰值的具体优化候选。
- `format/pdf/document_il/midend/layout_parser.py:171`：使用 `ThreadPoolExecutor(max_workers=os.cpu_count())`，会绕过只调翻译并发的措施。
- `format/pdf/translation_config.py`：任务创建配置时加载布局模型；未指定翻译线程数时会从 QPS 推导。
- `assets/assets.py:warmup`：预热涉及模型、字体和 CMap；不能简单删掉字体下载后宣布功能等价。

### 1.2 已核实的尺寸，不等同于性能基准

- 当前 `dist/PDFMathTranslate-Setup-2.9.0.exe`：**237,695,495 字节，约 226.7 MiB**。
- 当前 `launcher/publish/PDFMathTranslate.exe`：66,250,996 字节，约 63.2 MiB；包含自包含 .NET 等内容，不是纯业务代码体积。
- 开发环境中较大目录：`cv2` 约 112 MiB、`scipy` 约 93.3 MiB、`scipy.libs` 约 19.3 MiB、`pymupdf` 约 46.9 MiB、`onnxruntime` 约 37.8 MiB、`onnx` 约 30.6 MiB、`sklearn` 约 30.5 MiB、`skimage` 约 21.2 MiB。
- 上述目录数值包含开发环境内容，不是“各包在安装器中的压缩贡献”，更不是可直接删除的空间。
- 开发目录仍有约 160.6 MiB 的 Gradio，但标准安装包已排除它；再次删除开发环境不能算产品精简收益。
- 模型/字体首次下载、下载后占用和预览/翻译缓存，均应另外统计，不隐含到安装器数字里。

包体专项子代理的只读盘点补充：`webui` 全目录约 1.92 MiB；本机已有 BabelDOC 字体缓存约 253.49 MiB、布局模型约 71.84 MiB、CMap 约 7.35 MiB、tokenizer 约 3.45 MiB。这是本地缓存样本，不是新用户必需下载量的保证。按现有发布排除规则估算，Python site-packages 约 536.16 MiB 未压缩；这些估算在 P0 须用最终 payload 字节清单重算。

本机硬件已只读核实：Intel Core Ultra 7 255HX，20 逻辑处理器，约 15.5 GiB 可用物理容量，RTX 5060 Laptop GPU + Intel 核显。显存容量和实际可用 GPU provider 尚未实测。优先按 **16 GB 内存、均衡档**设计，不把 20 核直接等同于可开 20 个文档/计算线程。

**本轮没有运行翻译性能基准。本文所有延迟、内存、降幅指标都是待验证目标或策略初值，不是已经取得的结果。**

### 1.3 必须保留的既有成果

- 首页与队列共用任务快照、活动任务接续、运行任务优先选择。
- 取消排队任务与任务启动之间的原子状态保护。
- 目标语言/引擎配置、错误反馈和更新校验相关既有修复。
- 默认保存目录、首次导出选目录、`PDF名_yyyy-MM-dd` 文件夹、多版本不覆盖。
- 中文安装和卸载、自选安装路径、更新文件关闭后再做 SHA256 校验。
- `.pyi` 不能全删：lazy_loader/scikit-image 运行时需要；`testing` 不能按名称全删：NumPy 有公开导入。

当前工作树有此前修改。执行 AI 必须先保存状态清单、阅读现有差异；不得 `git reset --hard`，不得直接覆盖上述修复。

## 2. 先复用哪些项目

2026-09-28 已通过本地代理查询下列 GitHub 项目；实现时需固定正式版本或 commit，不使用浮动 main。

| 来源 | 复用范围 | 不照搬的部分 |
|---|---|---|
| [lepoco/wpfui](https://github.com/lepoco/wpfui) | FluentWindow、导航、主题、对话框、图标、基础控件；以 `samples/Wpf.Ui.Demo.Mvvm` 或 Fluent 模板为起点 | 不搬整个 Gallery、示例页面、Toast/Tray/Hosting 等未用模块 |
| [CommunityToolkit/dotnet](https://github.com/CommunityToolkit/dotnet) | `CommunityToolkit.Mvvm` 的 ObservableObject、ObservableProperty、AsyncRelayCommand | 不另写通用 MVVM 框架，不为简单状态引入多个状态管理库 |
| [funstory-ai/BabelDOC](https://github.com/funstory-ai/BabelDOC) | 沿用排版、公式、字体、布局处理；通过可复现补丁暴露线程与加载选项 | 不直接升级主分支替换现有稳定引擎，不静默删算法 |
| [microsoft/onnxruntime](https://github.com/microsoft/onnxruntime) | 使用现有 ORT 的线程、provider、会话配置能力 | 不编写推理引擎，不默认打包全套 GPU 依赖 |

WPF UI 是社区 MIT 项目，不是微软官方 UI 框架。CommunityToolkit 的许可证文件为 MIT。保留项目自身 AGPL-3.0、BabelDOC、PyMuPDF 及其他第三方的许可/NOTICE，发布前审查分发要求。复用控件不改变整个产品的开源义务。

已确认 WPF UI 当前 MVVM 示例针对 .NET 10，但示例主分支不等于已选 NuGet 稳定版。先做最小编译验证再锁定包版本。当前本地 `D:\paper\.dotnet-sdk` 只有 .NET SDK 8.0.414，实施时要准备 .NET 10 SDK；终端用户安装标准包不应再安装 SDK。

只选择一套主题来源：WPF UI 控件/资源字典为主，不叠加另一套 Material/Fluent 主题库。字体用系统 UI 字体与中文回退，避免捆绑大字体库和依赖未授权的 Windows 字体拷贝。

## 3. 目标结构与职责

```text
PDFMathTranslate.exe / WPF UI
  ├─ View / ViewModel：工作台、队列、结果、术语表、设置
  ├─ TaskStore：各页面和任务栏共享的客户端状态
  ├─ BackendClient：HTTP / SSE；不含翻译算法
  ├─ ExportService：本机保存、另存为、打开目录
  └─ BackendSupervisor：启动、重连、取消、关闭、拥有进程的生命周期
          │ 127.0.0.1 + 本次运行的鉴权 token
          ▼
轻量 Python 控制进程
  ├─ 配置、任务调度、历史、资源下载管理、健康检查
  ├─ 受限预览请求 → 按需隔离渲染进程（串行、空闲退出）
  └─ 文档队列 → 翻译 worker（首期最多 1 个）
                 └─ BabelDOC / ONNX / PDF / 远程翻译客户端
```

### 3.1 建议目录，不要求把小项目拆成十几个工程

```text
desktop/
  PDFMathTranslate.Desktop/        # WPF 主项目
    Views/ ViewModels/ Services/ Models/ Resources/
  PDFMathTranslate.Desktop.Tests/
source/pdf2zh_next/
  http_api.py                     # 薄路由，逐步提取既有业务
  desktop_api/                    # 健康检查、协议、事件、鉴权
  runtime/                       # worker bootstrap、资源策略、生命周期
  services/                      # task/asset/preview/history 等
  config/ translator/ high_level.py  # 沿用并逐步抽取，不一次全改
build/
  build-release.ps1 installer.iss
  dependency-locks/               # 标准发行依赖锁与哈希
  patches/babeldoc/               # 可审查补丁；或使用锁定 fork wheel
tests/performance/
docs/benchmarks/
```

不引入 Kafka、Redis、Docker、独立数据库服务、消息总线框架。任务持久化在本机；大历史量时可使用 Python 标准库 SQLite，避免 C#、Python 两侧同时写同一份状态。

### 3.2 配置和数据所有权

- Python 是引擎设置、任务、历史、资源包状态的唯一写入方。
- WPF 是窗口位置、面板尺寸等纯 UI 偏好的写入方；与后端共用的默认导出目录走 API，避免两边竞争改 JSON。
- 每个任务在入队时保存不可变有效配置快照，至少包含语言、引擎标识、模型、输出选项、术语表指纹、资源档位；不把 API 密钥复制到历史。
- 中途更改全局设置只影响新任务。重试明确选择“沿用原配置”或“使用当前配置”；不静默替换。
- 凭据至少使用当前用户权限保护，后续可迁移 DPAPI；不得将密钥放在日志、SSE、命令行参数、诊断包或普通任务历史中。
- 新 WPF 与旧 WinForms/兼容入口共享单实例约束，迁移期兼容现有 `Global\PDFMathTranslateNextSingleInstance` 互斥标识，不能只防止两份新 UI 同时启动。控制进程对实际数据目录再持有独占写锁；第二入口应激活原窗口或说明旧版本仍运行，不新建第二个写入者。支持多便携目录是未来单独功能，首期不随意更改互斥语义。

### 3.3 通信：先复用，再做必要增强

保留现有 `/api/settings`、`/api/files`、`/api/tasks`、预览、输出、术语表接口的业务语义。新增的是版本化契约，不是立刻重写全部 API。

新增/扩展接口建议：

- `GET /api/health`：`api_version`、`instance_id`、运行版本、数据目录、控制进程就绪状态；不导入模型。
- `GET /api/capabilities`：已安装引擎、输出能力、有效资源策略、可用 provider；允许缓存，不为检测能力加载模型。
- `GET /api/assets/status`：缺失资源、下载阶段、已下载字节/总量、失败原因。
- 资源准备命令：显式准备/取消/重试；下载过程不能阻塞健康检查。
- `GET /api/events`：SSE；有连接 token、序号、重连与快照协议。
- 分页历史接口：活动任务单独返回；终态按游标分页，不能把历史所有条目放进每个进度包。
- 任务提交支持幂等键，防止超时重试创建两个翻译；取消、关闭操作设计为幂等。
- 导出回执接口：按 `export_id` 幂等记录任务/输出版本、实际落盘路径、大小与校验摘要、保存时间；不把 UI 提示当成可清理暂存的唯一依据。

安全约束：仅绑定 loopback；每次启动生成高熵 token，经受控管道或受限环境传递，不写普通日志；所有读写、预览和文件输出接口都校验，健康握手也要验证应用实例。限制 Host/Origin，不开放任意 CORS；随机端口不能替代鉴权。禁止任意路径读取/执行，上传和导出都做规范化与许可范围校验。普通 HTTP 请求明确绕过外网代理。

SSE 契约至少包括 `instance_id`、单调 `event_id`、`task_id`、任务 `revision`、事件类型和必要字段。UI 应：

1. 初次握手获取有版本号的完整快照，并从对应游标开始接收；服务器须保证订阅切换期间不丢事件。
2. 同一任务拒绝旧 revision；完成/失败/取消为可靠终态，不能被晚到进度覆盖。
3. 重连使用 Last-Event-ID；缓存窗口不覆盖时明确 `resync_required` 并重新拉取快照。
4. 服务重启改变 instance_id；重新对账，不把旧任务误认为仍运行。
5. 进度合并到每秒 2–4 次；终态和错误立即发送，不被节流丢弃。慢订阅者采用有界缓冲并要求重同步，不无限堆事件。
6. 仅一个订阅连接更新 TaskStore，所有页面绑定同一来源；任务栏可显示选中任务或汇总，但汇总规则必须固定并标注。

先保留现有轮询作为开发期或故障降级：前台活动 1–2 秒一次、后台约 5 秒、完全空闲停止；不能同时运行多套常规轮询与 SSE。命名管道可后续评估，但不是降低 CPU/内存的优先项，首期不要同时迁两种 IPC。

## 4. 前端优化：信息结构与原生体验

设计采用“文档工作台”而不是网页仪表盘。使用 redesign-existing-projects 的功能审计、状态完整性和层级方法；不照搬其面向营销网页的噪点、玻璃、背景图、视差等建议。该任务已明确要求原生迁移，因此不受技能中默认保留 Web 框架的建议限制。

### 4.1 页面职责

| 界面 | 常驻内容 | 按需内容 |
|---|---|---|
| 工作台 | 文件、源/目标语言、开始/取消、当前状态、原文/译文预览 | 页码、排版细项、输出版本、术语选项 |
| 任务与历史 | 虚拟化任务表、状态筛选、取消/重试 | 某个任务的有效配置、日志摘要、资源统计 |
| 结果 | 按源 PDF/日期聚合，单语/双语/术语表版本 | 保存、另存为、打开目录、缺失文件处理 |
| 术语表 | 现有导入、查看、管理能力 | 大表分页/搜索，不能一次渲染所有行 |
| 设置 | 翻译服务、资源档位、默认保存目录、外观 | CPU/请求并发高级设置、缓存、日志、更新 |

工作台布局：窄的可折叠导航；文档列表；中央文档预览；右侧可折叠参数栏；底部当前任务状态。窄窗口优先单文档预览，通过标签切换原文/译文；大窗口支持分栏对照，使用 GridSplitter，不挤成多个小卡片。

中文 UI 建议正文 14 DIP、辅助文字 12–13 DIP、标题 18–24 DIP，4/8 DIP 间距体系。系统浅/深色、高对比度、明确焦点与键盘顺序；单一强调色，少量语义状态色。不要把文本/按钮整体缩小来容纳高级参数。

### 4.2 关键交互规格

- 主窗口先出现；模型准备和下载在可见状态区域显示，支持重试，不用无限“启动翻译引擎”占满主界面。
- 目标语言常驻可见。首次使用显示默认值，例如“简体中文（默认）”；若采用必须选择策略，则必须阻止提交空值。不得 UI 显示空白、后端默默沿用 `zh`。
- 开始前显示有效引擎、目标语言、输出种类。引擎未就绪时解释原因，允许资源准备，但不把没有输出的任务标为完成。
- “翻译完成”和“已保存到用户目录”是不同状态。输出文件存在不等于用户已经导出。
- 原生多选文件/文件夹对话框、拖放导入、Ctrl+O、Ctrl+S、Esc、可取消的长操作；重复打开激活已有实例而非再启动后端。
- DPI 100%/125%/150%/200%、多屏移动、窗口位置恢复、缩放后仍可操作；跨显示器时校正窗口到可见区域。
- 关闭时若有任务，提供“继续在后台/取消并退出/返回”；托盘后台是显式选择，默认不偷偷常驻。显式退出必须回收所拥有进程。
- 首期 PNG 预览支持翻页、缩放、原译切换/对照，不宣称能复制文本或全文搜索。完整 PDF 阅读器作为独立后续需求，届时优先找可复用组件并评估许可证与体积。

### 4.3 WPF 性能约束

- MVVM + AsyncRelayCommand；UI Dispatcher 禁止执行网络等待、PDF 解析、同步磁盘扫描、`.Wait()`/`.Result`。
- 列表开启容器回收虚拟化；不要外包一个无限尺寸 ScrollViewer 破坏虚拟化；分页加载历史。
- ObservableCollection 增量更新，不在每个进度事件全量替换；批量通知，避免多层 ValueConverter 重复计算。
- BitmapImage 按显示尺寸解码，使用合适的 DecodePixelWidth；后台读取，OnLoad 后关闭流，可冻结则 Freeze；离开页面解除图像引用。
- 每个页面的订阅/计时器/取消令牌有明确释放点；切换页面不新建一个独立后端客户端和任务轮询。
- 不用 CompositionTarget.Rendering 做常驻刷新；隐藏/最小化停止动画和邻页预取，不隐藏翻译状态本身。
- 不默认大面积透明、BlurEffect、持续阴影动画。保留系统正常硬件合成，不能用强制软件渲染换来更高 CPU。
- 资源面板只有打开时约 1 秒刷新，关闭后不高频监测全机进程/GPU。

## 5. 启动、进程、就绪状态优化

### 5.1 状态机

`窗口可用 → 控制接口启动 → 读取配置/历史 → 资源检查 → 可翻译`

资源缺失进入 `等待准备/下载中/校验中/失败可重试`，不妨碍查看历史和设置。任务另有 `queued → preparing → running → finalizing → done`，以及 `cancelling → cancelled`、`failed`。引入新状态时同步 API、持久化和所有 UI 测试；迁移期不得让旧客户端把未知状态当成完成。

就绪检查用结构化 `/api/health`，替换解析 stdout 的 `WebUI ready:` 和请求根路径的脆弱条件。超时按阶段计算：控制进程启动与资源下载分离；有明确网络超时、重试和取消，不能把下载时长纳入固定 3 分钟启动限额。

### 5.2 真正做到按需加载

1. 增加独立 `start-engine.py`/桌面控制入口，不静态托管网页；原 Web 模式留在兼容入口。
2. 控制进程只导入配置、调度、协议模块。把 worker 入口移到轻量 bootstrap，进入子进程之后才 import BabelDOC/ONNX/NumPy 等重模块。
   PDF 页数读取、有效性检查和预览也交给渲染进程，避免上传后控制进程因 `_pdf_page_count()` 常驻 PyMuPDF；需要的资源扫描/下载模块如会导入重库，应拆轻量入口或单独短生命周期进程。
3. `high_level.py` 现有多进程和取消逻辑尽量保留；拆除父进程为拿到 spawn target 而导入重依赖的耦合。Windows spawn 须验证 `__main__`/freeze_support，不重复启动控制进程或线程池。
4. 资源管理按当前能力识别必需模型、字体和 CMap；翻译前强校验，后台检查不得导致多个任务重复下载同一资源。
5. 暂不能精确识别必需字体时，先后台准备原有完整资源并提示大小；不要冒险删字体。按语言细分属于后续独立质量验证项。
6. 下载支持断点/临时文件、校验哈希、原子完成标志、单资源锁、超时和取消。没有完成标记的临时资源不得被加载。
7. 不使用开机自启或 Windows 常驻服务来制造“热启动快”的假象。

退出由 BackendSupervisor 协作通知，等待有界时间，再终止该应用拥有的进程树；考虑 Windows Job Object 的 kill-on-close，并验证 worker 后代归属。不能按进程名杀全部 python.exe。父进程异常退出也要有 worker 清理路径；必须覆盖正在写 PDF、等待远程请求、资源下载和 IPC 阻塞几种情况。

## 6. CPU 优化：分开控制三种并发

三种不同参数必须分别命名：

- `document_concurrency`：同时翻译多少份文档，决定模型/PDF 数据份数。
- `local_compute_threads`：布局、数值计算等本地线程预算。
- `api_inflight_limit` / `api_qps`：远程请求的在途数/每秒发送数，不是本地 CPU 线程数。

### 6.1 初始资源档位

下表是可调整的初值。L 为逻辑处理器数；预算至少为 1；低内存/高压力会进一步减少接纳任务。

| 参数 | 节能 | 均衡（默认，适合本机） | 性能（显式选择） |
|---|---:|---:|---:|
| 文档同时运行 | 1 | 1 | 默认 1；测得内存充足时允许 2 |
| 本地计算预算 | min(2, L) | max(1, min(4, L-2)) | max(1, min(8, L-2))，测试后可高级调节 |
| 远程在途请求初始上限 | 4 | 8 | 16，仍受服务配额约束 |
| 请求 QPS 档位初始上限 | 2 | 4 | 8 |
| 预览渲染并发 | 1 | 1 | 1 |
| 邻页预取 | 关闭 | 空闲时最多相邻 1 页/方向 | 同均衡，不无限预取 |
| 首期模型驻留 | 随任务 worker 退出 | 随任务 worker 退出 | 随任务 worker 退出 |

实际 QPS 取用户值、服务配额和档位上限的较小值；不能把 QPS 与在途数混为一谈。“每种库各开 4 线程”不等于总预算 4。必须按阶段/嵌套关系分配：页面外层并行时内层 BLAS/OpenCV 通常设 1；单个 ONNX 会话运行时按计算预算分配 intra-op，inter-op 先设 1。不同子系统可并发时共享总预算或减少各自预算。

### 6.2 参数必须真正传到底层

- ORT `SessionOptions.intra_op_num_threads`、`inter_op_num_threads`、执行模式；节能档评估关闭 intra/inter-op 空闲 spinning。用测量确认延迟/功耗，不把参数存在当作已生效。
- 在相关库导入前给 worker 设置 `OMP_NUM_THREADS`、`MKL_NUM_THREADS`、`OPENBLAS_NUM_THREADS` 等适用变量；用 threadpoolctl/实际线程统计确认后端，不在 UI 进程全局污染环境。
- OpenCV 使用 `cv2.setNumThreads()`；独立验证其与外层线程池的嵌套。
- 将 BabelDOC layout_parser 的 `os.cpu_count()` 改为有默认兼容值的显式参数；不 monkeypatch 全局 `os.cpu_count()`。
- 减少创建过多 page futures：有界提交窗口/背压，而不是把全部页面一次提交给 executor。文档待运行队列也要有上限和明确反馈。
- 服务建议 QPS 是建议，不是覆盖用户资源预算的命令。修复 `SiliconFlowFree qps=20` 及 recommended 参数覆盖链，在最终创建引擎时应用统一策略，并回报“请求值/服务限制/最终值”。
- 同服务、同账户的术语提取和正文翻译共享限流预算；两个文档不能各自都用完整服务配额。跨 worker 可由控制进程分配配额或统一令牌发放，避免各建独立 limiter 后总量翻倍。
- 429/超时使用有上限的指数退避与抖动，尊重 Retry-After；等待不 busy-loop；取消能中断重试。连接池和在途请求数匹配，不为每段文字新建客户端。

对纯 Python CPU 热点、DBSCAN 等算法只有 profiler 证据后再优化；不要先改底层聚类近似算法。线程上限不是严格 CPU 百分比限制。Windows 优先级/EcoQoS 可后续评估，不默认绑定核、不默认硬 CPU 限额、不承诺“运行永远不超过 20%”。

## 7. GPU：默认不抢资源，按需且可验证

当前 Windows BabelDOC 只使用 CPU provider，因此“优化 GPU”首期是防止 UI 合成/预览造成无谓 GPU 占用，而不是寻找不存在的默认 CUDA 推理。

### 7.1 默认模式

- WPF 使用系统合成与正常硬件加速；静止界面不连续重绘，最小化不播放动画。
- 预览维持 PyMuPDF CPU 渲染；不为了“使用 GPU”额外引入第二套大渲染库。
- 安装包不带 CUDA/cuDNN、PyTorch、本地 LLM、多个互斥 ORT 分发版。
- UI 3D/合成与 ML Compute/CUDA 的指标分别统计，不能把全部 GPU 活动算成翻译推理。

### 7.2 可选实验 GPU 包（P4，不阻塞标准版）

只有布局推理已被证明是主瓶颈时，才做独立受控试验：

1. 锁定 GPU runtime、驱动兼容矩阵、模型和 provider；CUDA 与 DirectML 分开验证。
2. 修改当前 CPU-only 选择逻辑；不能只安装 `onnxruntime-gpu` 就宣称启用成功。
3. 标准 CPU 环境与可选 GPU 环境隔离，避免 `onnxruntime` / `onnxruntime-gpu` / `onnxruntime-directml` 混装同一命名空间。
4. 显示实际 provider；加载失败给出原因并允许回退 CPU，不在用户不知情下重复执行已收费远程翻译。OOM 的重试以任务/阶段检查点为边界，不无限重试。
5. 仅创建必要的会话；没有任务后随 worker 退出释放 GPU 资源；设置软显存预算，说明 provider 参数不一定覆盖所有驱动分配。
6. 比较总耗时、CPU 时间、峰值内存、专用/共享显存、功耗/风扇与布局输出质量。如果只是 CPU 下降但显存/功耗/包体大增、端到端无明显收益，维持默认 CPU。

量化、半精度、改变输入分辨率、替换模型均属于可能改变识别质量的算法试验；单独实验分支和文档集验收，不能作为默认“无损精简”。远程翻译发生在服务端，本机 GPU 不会普遍加速远程 API 等待。

## 8. 内存：减少常驻与叠加，不伪造工作集

### 8.1 高收益、低风险优先

1. 默认文档并行 2 → 1，最直接减少模型和文档中间状态叠加。
2. 重依赖只进入 worker，控制进程不常驻布局/科学计算模块。
3. WPF 和预览缓存都按字节计量；历史分页；任务内存不无限累积。
4. PDF/图片流用完关闭；本机输出保存走文件流/CopyToAsync，禁止整份 PDF 读成 byte[]/Base64 再跨 IPC。
5. 现有上传已按 1 MiB 分块读取，继续保留；原生导入首期也流式上传，暂不增加允许任意本地路径的危险接口。
6. worker 生命周期明确，退出回收 ONNX/native allocations；检查线程、管道、日志队列的关闭次序，先发结束信号再等待日志线程，避免每次任务多等超时或泄漏。
7. 任务注册表只保留活动任务和有界最近终态；完整历史留磁盘。活动任务的持久化不受“最近 50 条”限制，不能大量入队后把较早活动任务从快照挤掉。持久化先修为临时文件 + 原子替换、锁与 schema version；需要大量历史时再迁 SQLite + 单写入方。跨进程日志/进度队列亦需有界或合并，终态与错误可靠传递，避免仅限制 UI 队列但 worker 通道无限增长。

### 8.2 ONNX 模型加载候选

Windows CPU 路径试验从 `InferenceSession(model_path, sess_options=..., providers=...)` 直接加载，使用 `get_modelmeta().custom_metadata_map` 取 stride/names，避免先构造 ONNX 模型对象再序列化一份 bytes。

验证：元数据解析、输入/输出 shape、布局结果、首次加载峰值、重复加载与错误消息。Darwin 的静态形状改写逻辑不能被无条件移除。确认 Windows 所有已声明能力均不再需要 `onnx` 后，才能在 Windows 专用依赖闭包中移除它；同时修改受控包 metadata，不能仅删目录骗过依赖检查。

### 8.3 分块与内存压力

- 首期使用引擎已支持的分块策略，以 50 页档位试验；并非所有 PDF 都会随页数线性占用，不能只用文件 MB 大小估算内存。
- 10/20 页更细分块需要修改当前 >=50 的校验和引擎兼容性，验证跨页术语、目录链接、页码、输出合并、对象资源复用之后才开放。
- 调度器综合可用内存、既往同类任务峰值和用户档位。初始策略：系统可用内存低于 max(1 GiB, 总内存 10%) 时，不启动新 worker，关闭预取、缩减缓存并提示；恢复阈值更高且持续一段时间后再放行，防止抖动。
- 对正在运行的大文档，不用粗暴强杀来实现软内存预算；提示、用户取消或在已支持的安全分块边界暂停。尚无安全 checkpoint 时，不伪造“暂停/续传”按钮。
- 显式取消先协作，超时才终止所拥有 worker；临时输出与最终输出分离，不能把半成品当成功结果。

### 8.4 worker 复用是后续取舍，不是首期必做

现有每任务新进程开销较高，但结束后能回收模型与 native 内存。先保留这一优点。只有批量短任务基准证明加载成本显著时，再考虑单 worker 连续处理任务、空闲 60–120 秒后退出、处理 N 个任务或内存异常增长后回收。

复用前必须验证引擎模型和任务上下文可重入、清理、取消、配置隔离；不在现有 per-task worker 外再建一层同样加载模型的常驻服务。节能档仍以任务结束释放为默认。

禁止循环 `GC.Collect()`、强制 EmptyWorkingSet、禁用系统缓存、频繁重启进程来美化任务管理器；验收同时看 private bytes、工作集和系统 commit，不能只挑好看的一个数。

## 9. PDF 预览专项优化

这是与翻译无关、可独立取得收益的一组任务。

### 9.1 渲染与并发安全

- PyMuPDF 不按普通线程安全库对待。HTTP 多个请求不得随意并行调用共享 Document，不能只用 GIL 当保护。
- 推荐一个按需渲染进程，内部串行操作；独立于翻译 worker，超时/崩溃不拖死 UI/控制进程。无文档可预览一段时间后退出。
- 首期允许每请求安全打开/关闭 PDF 并缓存结果；跨请求保留文档句柄是可选优化，必须限制数量并处理文件变更/删除。
- 队列“当前页优先，旧预取可丢弃”；原生调用中的渲染未必可立即取消，至少取消排队项并丢弃过期结果。硬超时才回收渲染进程。

### 9.2 有界缓存设计

缓存键：`document_id + content_revision/hash + output_variant + page + rotation + render_size_bucket + renderer_version`。不能只按文件名缓存，同一文件的多个译本不能串页。

初值：

- 宽度档位如 900 / 1400 / 2000 像素，按 DPI/显示尺寸选择；缩放操作 debounce 150–250 ms。
- 单页最长边 <= 8192、像素总量 <= 12 MP，两个条件同时约束；超限等比缩小并提示，不裁掉正文。后续高倍率可做分块，不首期预留无限全页图。
- WPF 已解码图像 LRU：节能 64 MiB、均衡 128 MiB；按实际 stride×height 与保留引用核算。12 MP 的 BGRA 图本身约 48 MB，不能拿压缩 PNG 大小估算内存。
- Python 缓存以压缩 PNG/文件为主，内存先限制 32–64 MiB；磁盘预览缓存初值 256 MiB，超额 LRU 清理。
- 最多保留当前页和少量邻页；列表缩略图低分辨率、仅可见区域加载。200 页文档不能开头就渲染 200 页。
- 使用内容版本 ETag/私有缓存语义，替换一律 `no-store`；保留鉴权，不让敏感 PDF 缓存进入公共代理。

UI 只在文档/页/尺寸变化时取图，不跟随进度事件重新取图。PDF 译文不一定与原文页数/页序相同；双语并排与上下拼接不能靠“页号一样”盲目同步，必要时依据输出模式映射并明确显示。

## 10. 安装包与依赖精简

### 10.1 先把“臃肿”拆开统计

发布报告必须列：安装器压缩体积、安装后二进制体积、首次资源下载字节、资源下载后体积、用户文档/输出、缓存/日志、运行 private bytes。换 UI 主要影响前端与常驻进程，不能保证科学计算/PDF 依赖随之消失。

### 10.2 低风险精简（P0 审计，P3 标准包落地）

1. 从 `source/pyproject.toml` 和新的桌面发行锁创建洁净运行环境，不复制开发 venv 后凭名字删库。
2. 将 Web/Gradio GUI、测试/文档工具、可选服务 SDK 做依赖分组。保持标准版原有公开服务可用；若选择最小引擎版，必须另列能力表，不默默减少已有功能。
   `tomlkit`（配置读写）、`python-multipart`（文件上传）需要显式直接依赖；`narwhals` 等已在必要依赖闭包内的包不能误当 UI 附属品，`httpx[socks]` 对应的 `socksio` 也要保留到代理测试通过。
3. 保留已完成的单套 Python 与默认排除旧 Gradio策略。仅移除默认桌面版真正不用的静态 Web UI 和 WebView2 引用/检测逻辑；开发兼容入口不必删除。
4. 检查 `gradio_i18n` 是否仍被非 Web 模块依赖。若要去掉，先用轻量 gettext/适配层替换完整调用链并测试，不直接删包。
5. 去掉发行物中的源码映射、开发缓存、未用示例、编译中间产物与符号；调试符号单独归档。许可证、dist-info 元数据和必要资源必须保留。
6. 不对所有包无差别剥除 `test/testing/.pyi`。以洁净环境功能测试决定排除项，记录原因和回归测试。
7. OpenCV 当前已经是 `opencv-python-headless`；不能把“换 headless”当成尚未执行的主要收益。
8. 不打包 GPU 运行时、不打包全套本地 LLM、不同时带多套 Python/.NET。

### 10.3 深度候选（P3 依赖审计；涉及引擎/算法改动的进入 P4）

| 候选 | 预期收益方向 | 准入条件 |
|---|---|---|
| Windows CPU 直接从模型路径创建 ORT Session | 加载峰值下降；可能去掉 `onnx` 工具依赖 | 模型元数据/输出一致；所有 Windows 能力依赖审计；修正 metadata |
| `pandas`、`hf_xet`、未用 SDK 等 | 可能减少包体/冷导入 | 上游闭包、可选引擎、导入动态路径和资源下载测试，不能仅看本项目无 import |
| 字体/模型按需资源包 | 减少首次不必要下载和磁盘占用 | 语言/字体完整性、断网恢复、哈希校验；未准备资源明确提示 |
| 自编精简 OpenCV/替换 DBSCAN 或 SSIM 依赖 | 可能较大，但维护/质量成本高 | 精确 API 使用清单、Windows wheel 构建、安全更新、PDF 输出回归；不首期做 |
| 模型量化/替换 | 模型体积和计算变化 | 独立识别质量指标，不能声称天然无损 |

SciPy、scikit-learn、scikit-image、OpenCV、PyMuPDF 当前都有实际作用。删 DBSCAN、扫描检测或排版保护属于功能/算法变更，不是清理垃圾文件。当前运行包中的 OCR/table 路径也可能已被裁剪或禁用，不能先假定存在一个巨大 OCR 模型可以删；先列真实加载资产。

### 10.4 .NET 发布设置

- 优先 `.NET 10 + win-x64 + SelfContained=true + 多文件发布`。用户看到的是一个安装程序，应用无需也是单文件；多文件有利于避免单文件解压与压缩加载开销。
- A/B 测试 `PublishSingleFile`/压缩以及 ReadyToRun 的启动与体积，不能把 ReadyToRun 默认当精简手段。
- WPF 不作为 NativeAOT/激进 trimming 的常规支持目标；首期不开 `PublishTrimmed`，不追求 AOT 以免破坏 XAML/反射/资源。
- `build-release.ps1` 当前只复制发布的 EXE。改为多文件后必须复制整个洁净 publish 输出及资源/依赖；不能只替换 EXE 然后交付缺 DLL 的安装器。
- “轻量在线版”可后续依赖已安装 .NET Desktop Runtime、按需引擎包；必须另算安装时实际网络与磁盘成本，不能把下载搬到首次运行就称为总体减少。
- 标准版优先自包含，保留无需用户配 Python/.NET 的体验。VC++ 运行库等 native DLL 依赖在干净机器检查，缺失时提供中文处理流程。

Python venv 本身不天然可搬迁。现有 `pyvenv.cfg` 含开发机绝对路径，新的构建必须明确采用可重定位解释器 + 相对目录/bootstrap 的布局，或受测的配置重写机制；验证复制到另一盘符、中文/空格路径后无需开发机目录即可导入全部 native DLL。不要把洁净 venv 原样打包就认定支持任意安装路径。

安装器 `lzma2/normal` / 非 solid 可与更高压缩、合理 solid 分组做 A/B。它只影响下载和解包，不是运行内存优化；同时记录安装耗时、解压峰值 RAM 与升级代价，不只追最小 EXE。

### 10.5 可复现构建要求

生成锁文件、版本/哈希清单、每目录/依赖字节报告、许可证清单/SBOM、补丁清单。验证干净构建的安装包能运行，而不只验证开发目录。

第三方修改通过 fork wheel 或版本化 patch，在构建时应用并验证哈希；禁止仅手改 `site-packages`。构建 staging 使用明确唯一目录，失败也能安全清理；清理前验证绝对路径在 staging 根之下。不得使用未校验的递归删除，更不能复用当前脚本的宽泛 CleanDist 行为作为常规清理方案。

发布必须升级版本，保留旧安装器供回退。标准版验收前不覆盖现有 `dist/PDFMathTranslate-Setup-2.9.0.exe`。

## 11. 数据目录、保存版本与磁盘治理

### 11.1 统一目录解析

安装模式：程序文件只读；配置、历史、临时文件、日志、模型缓存位于 `%LOCALAPPDATA%\PDFMathTranslate\` 的明确子目录。便携模式用明确标记或选项选择 `home\`，不要仅凭“当前目录能写”就猜成便携模式。

启动器确定路径并通过专用参数/变量传给后端，握手返回实际目录。禁止 C# 一套 fallback、Python 一套 fallback；不在整个 UI 进程重设 HOME/USERPROFILE 等系统变量。引擎兼容所需路径重定向限于自己的子进程，并优先改为库支持的显式缓存参数。

迁移：检测旧 `home`/`pdf2zh_files`/配置，展示来源；备份并拷贝、验证后切换；写迁移版本标记，幂等可重入。历史中的绝对输出路径做存在性对账，不盲目字符串替换；保留旧数据到用户确认或回退窗口结束。

### 11.2 输出保存规则

```text
用户选择的默认保存目录/
  原PDF名_2026-09-28/
    原PDF名_双语.pdf
    原PDF名_单语.pdf
    原PDF名_术语表.csv
    原PDF名_双语 (2).pdf
```

- 默认目录在首次保存前选择并持久化；设置页可随时更改，每次也可“另存为”。显示本次完整落盘目录。
- 日期采用用户本地日期，默认以翻译完成日期归档并在任务中保存；旧实现按保存当天取日期，迁移时明确新规则且不移动已有导出文件。
- 同名但不同源 PDF 必须有不同 document_id/content hash，UI 不误合并；同日目录冲突仍保留版本信息，必要时加短后缀并说明。
- 版本依据原文标识、语言、引擎/模型、输出种类、任务时间关联，不仅看文件名。用户可见名称仍遵循 `PDF名_日期`。
- 清理非法字符、Windows 保留名、末尾点/空格、过长路径；中文、Unicode 和 UNC 目录必须测试。
- 不覆盖已有文件。用独占创建/预留或等价原子方式处理并发命名，不能“检查不存在后直接覆盖”。流式写 `.partial`，完成校验后原子提交；跨卷复制失败保留可重试源文件，不产生伪成功条目。
- 保存完成后 WPF 以稳定 `export_id` 向后端提交回执，后端校验输出身份并持久化导出记录。回执失败时 UI 区分“文件已保存/记录待同步”，用本地有界持久待办重试同一回执，不能重新复制产生 `(2)` 文件。后端只有取得持久记录、满足保留策略并完成必要的文件存在/一致性复核后才允许清理暂存；外置盘暂离线不能被当作可清理依据。
- 首期保留后端输出暂存 + 用户显式导出，确保可恢复。后续直接生成到目标目录必须另外验证权限、中断恢复与原子提交，不能为了少一份文件就破坏可靠性。

### 11.3 保留策略

| 数据 | 建议规则 |
|---|---|
| UI 位图/预览缓存 | 有界 LRU，随内存压力缩减，用户可清理 |
| 下载 `.partial`/失败中间产物 | 无活动引用时才清；提供过期 TTL，启动后低优先级治理 |
| 上传原文 | 活动任务及可重试历史引用期间保留；删除前解释重试/预览影响 |
| 后端结果暂存 | 在导出成功且无保留需求后按策略清理；未导出结果不自动当垃圾删 |
| 用户导出目录 | 不由自动缓存清理或卸载清理，删除只能由用户明确请求 |
| 模型/字体 | 按版本与引用管理；不混入一般临时缓存，避免频繁重新下载 |
| 翻译缓存 | 保留命中收益；核实 key 包含引擎、模型、语言、提示词/术语变更；有界、可查看和手动清理 |
| 日志 | 初值 5 文件 × 5 MiB，轮转与脱敏，诊断包不带原文/密钥 |

“清空历史”只清终态记录，不清正在运行的任务，不取消翻译，不删除输出。当前 `/api/tasks` 的清空实现会清整个注册表，需修正并补回归测试。大目录统计异步、按需、可缓存，不能每秒递归扫描缓存目录。

- 保留现有 Inno Setup AppId，测试覆盖安装能识别旧版本、沿用用户目录；不另起一个新产品 GUID 留两个卸载项。

- 升级前检查自己的活动任务和进程，允许稍后更新；优雅退出后再替换文件，禁止更新中把翻译 worker 和旧 DLL 混用。

## 13. 测量方法与验收目标

### 13.1 先测，再改，每阶段都保留基线

新增不依赖真实收费服务的 benchmark harness：可控 mock 翻译服务用于可重复 CPU/内存/状态测试；真实服务小样本验证单独执行并需要用户提供配置，不擅自发起大量收费翻译。

固定输入 PDF 的 hash、引擎/模型/字体版本、机器/驱动、电源模式、DPI、线程配置、输出选项。缓存冷/热分组；首次网络下载单独记账。不能把“优化后命中缓存”与“优化前首次调用远程 API”比较。

测量矩阵：

| 场景 | 关键指标 |
|---|---|
| 冷启动（程序缓存冷，资源已准备）/热启动 | 首窗、可交互、API ready、引擎 ready 分别计时 |
| 首次资源缺失/下载失败/断网启动 | UI 不阻塞、真实下载进度、取消和重试 |
| 空闲 5 分钟、最小化 5 分钟 | 整个进程树 CPU、内存、GPU、唤醒/请求数 |
| 10 / 50 / 200 页；文字/公式/表格/扫描输入 | 端到端时间、各阶段 CPU 时间、模型装载峰值、内存峰值 |
| 一份大文档/批量 10 份/重复 20 次预览打开关闭 | 资源增长趋势、句柄/线程/进程数、缓存上限 |
| 取消排队/模型初始化/网络等待/写文件阶段 | 响应延迟、进程回收、半成品标记 |
| 后端崩溃/SSE 断连/重启/磁盘满/权限拒绝 | 状态一致、恢复、无重复提交和覆盖 |
| 正常退出/强制关闭窗口进程 | 所拥有后代进程最终清零，无用户输出丢失 |

采样：通常 1 秒一次，峰值敏感场景 100–250 ms，分别记录采样开销。用 WPR/WPA、PerfView/dotnet-counters 和 Python/系统进程指标定位；工具按需要选，不全加入发行包。PyMuPDF/ONNX 的 native 分配不能仅用 tracemalloc 解释。

每个进程记录 PID/父 PID/角色、private bytes、working set、线程/句柄、CPU 时间、I/O；总计仅限本应用进程树。归一化 CPU = `进程树 CPU 秒增量 / (墙钟秒增量 × 逻辑处理器数) × 100%`，同时提供 CPU 总时间，防止高核数掩盖绝对消耗。共享工作集相加可能重复计数，要标注统计口径。GPU 分开 3D/Compute 与专用/共享显存，并考虑 DWM 归属，不声称 WPF 空闲 GPU 必定为零。

### 13.2 建议验收门槛（先基线校准再锁定）

| 指标 | 初始目标 | 说明 |
|---|---|---|
| 热启动原生窗口可交互 | P95 <= 1.5 秒 | 资源下载、模型初始化不在此计时，但另有可见状态 |
| 本地冷启动窗口可交互 | P95 <= 3 秒 | SSD 参考环境，记录杀软/首次 JIT 情况 |
| 无任务空闲 CPU | 稳态 5 分钟平均 <= 0.5%（上述归一化口径） | 整树，不只 UI；同时对比 CPU 秒 |
| 空闲 private bytes | UI + 控制进程初步争取 <= 250 MiB | 无打开文档、worker 已回收；若基线不支持需解释并调整，不能造假 |
| 同样本翻译峰值内存 | 相对当前同并发/同质量基线争取下降 >= 20% | 另报默认并发 2→1 的产品场景改善，不能混成算法收益 |
| 同样本均衡模式吞吐 | 同为 1 文档并行时，相对基线尽量不慢超过 10% | 单列热/冷加载；节能档允许明确速度换低占用 |
| 已缓存翻页反馈 | P95 <= 150 ms | 缓存命中、固定预览大小；未缓存渲染另测 |
| 取消反馈 | UI <= 200 ms 给出“取消中”；通常 5 秒内回收 | 无法安全结束的阻塞需显示原因；超时策略不能伪报已取消 |
| 稳定性 | 连续任务结束后无单调内存/句柄/线程增长 | 观察 warm-up 后趋势和回收后基线，不要求 OS 工作集逐字节恢复 |
| 安装器体积 | P3 标准原生版尽量不超过 226.7 MiB；P4 争取相对原基线再减 10–20% | 完整标准能力、自包含运行时口径；不可用删功能/把下载外移冲指标 |

这些是工程目标，不是全部 PDF、硬件和网络环境的保证。不能同时承诺“速度更快、内存更低、包体更小、GPU 更省”而不列取舍。建议启动/交互样本至少 20 次统计 P95；长翻译至少 3 次报告中位数和范围，不用 3 次样本伪报有意义的 P95。

### 13.3 正确性与功能门槛优先于百分比

- 建立 golden 文档集：多栏、公式、表格、图片、长页、旋转、CJK/多语言、不同字体、目录/链接、加密/损坏 PDF、中文长路径。
- 页数、公式、图表、文字溢出、字体缺字、目录链接、单/双语及术语表逐项验收；PDF 二进制可能有时间戳差异，不只靠文件 hash 判质量。
- 进行原/译页面渲染抽样比对和人工关键页检查；在同样翻译文本输入下验证排版一致性。
- 50/200 页翻译需所有关键页和最终文件完整，不能仅证明第一张预览能显示。
- 覆盖已有 `source/tests/` 的配置/上传/任务错误等测试；不因为旧 GUI 被移出标准安装包就删除兼容源码测试。
- 最终必须从安装器在干净用户环境验证：无开发 venv、无系统 Python、无 .NET SDK；不以 IDE 运行成功替代。
- 迁移专项：旧入口运行时启动新入口、反向启动、重复启动控制进程均不得并发写同一数据目录；保存后断开 API、回执重复提交、导出盘离线的情况下，不重复复制、不丢已保存记录、不误清暂存。

## 14. 分阶段实施与交付顺序

每阶段结束都要求至少一个未主写该模块的子代理审核；先修复阻断项再进入正式发布。不要求每一步都同时并行，先冻结契约再分工。

| 阶段 | 主要工作 | 应提交的交付物 | 放行条件 |
|---|---|---|---|
| P0 基线与契约 | 保存工作树、性能基线、依赖/资产盘点、统一状态/路径/资源字段 | baseline 报告、API/event schema、迁移备份设计、依赖图 | 确定当前能力；不改输出语义；契约子代理审核 |
| P1 原生纵向切片 | WPF 模板裁剪，导入→语言→翻译→同源进度→预览→保存；轻量控制启动、鉴权 | 可运行原生开发版本、契约测试、失败/取消路径 | 真实单任务闭环；不依赖 WebView2；旧入口仍可用 |
| P2 资源治理 | 默认单任务、最终有效并发策略、BabelDOC线程参数、预览进程/缓存、退出清理、目录统一 | 性能对照、worker/预览单测、资源面板 | 限额真实生效，取消不留进程，质量无回归 |
| P3 功能齐备与包体 | 设置/队列/历史/结果/术语迁移、洁净依赖构建、安装升级/卸载 | 标准原生安装包、功能矩阵、字节报告、回滚包 | 全能力与安装矩阵通过；独立验收后才切正式默认入口 |
| P4 可选深度优化 | ORT直接加载、细分字体/资源、worker短期复用、GPU实验、算法替代 | 每项独立 A/B 报告、补丁、质量证据 | 有实际收益且风险可控，未通过就不合入默认版 |

P1 可以先通过兼容 API 验证闭环，但不能用“新 UI 已经出现”宣称整个迁移完成。P2 的依赖 import/worker 重构风险较高，应小步独立提交，不与大范围视图改名混在一个补丁中。

### 14.1 可交给多个 AI 的边界

共享协议先由主负责人提交，随后：

| 实施角色 | 文件/责任范围 | 验证责任 |
|---|---|---|
| AI-A 原生 UI | `desktop/` 的 View/ViewModel/主题；遵守已定 API | 键盘/DPI/状态/虚拟化、任务栏同步 |
| AI-B 控制层 | Python `desktop_api/services`、状态持久化、事件、鉴权、路径 | API契约、断连重连、幂等/取消竞态 |
| AI-C 引擎资源 | worker bootstrap、资源档位、BabelDOC受控补丁、preview | 线程/模型/内存/进程回收与PDF质量 |
| AI-D 发布与测试 | 构建锁、installer、benchmark、干净环境测试 | 包体、升级/卸载、功能矩阵、可复现 |
| 独立审核 AI | 只读复核实现、报告和用户路径；不默认接受作者结论 | 分级问题清单，核对测试证据；修复后复审 |

避免 B/C 同时改整份 `http_api.py`：先由 B 抽薄路由/协议，再各自在模块内落地，接口变更由主负责人统一。人数有限时按 P0→P1→P2 顺序串行，审核角色仍独立。

### 14.2 文件级改动清单

- 新增 `desktop/` 原生主工程和测试，不把 `launcher/MainForm.cs` 逐行改成 XAML code-behind。
- 从 `launcher/BackendRunner.cs`、`Program.cs` 提取端口、进程/日志/单实例思路；重写为异步有取消的 Supervisor，修正目录假设与粗粒度就绪条件。
- 从 `launcher/UpdateChecker.cs` 复用下载、哈希与已修复的句柄处理；UI 进度改绑定，不保留 WinForms 依赖。
- 拆分 `start-webui.py` 的环境设置与启动，新增 desktop 控制入口；完整 warmup 不阻塞 API。
- `http_api.py`：保持业务语义，拆调度/事件/历史/预览；任务清理仅作用终态；引入 task-specific output staging，避免同源多任务混用输出。
- `high_level.py`：重依赖后移、轻量 spawn target、取消/日志管道资源对称关闭、参数透传。
- `config/model.py` 与 `translator/utils.py`：新资源字段、最终有效策略、免费服务覆盖逻辑、配置快照；保留引擎兼容。
- BabelDOC patch：layout 线程池、ORT SessionOptions、可选直接模型加载；每项可单独回退。
- `source/pyproject.toml` / lock：发行依赖分组、显式 multipart 等直接依赖、许可证、可选能力；不只删文件。
- `build/build-release.ps1` / `installer.iss`：.NET10、多文件发布、洁净依赖、保留 AppId、去 WebView2 提示、发布清单、升级安全检查。
- `webui/` 和旧 `launcher/`：迁移期保留参考；完整验收后从标准包排除，不在早期删除源码。
