PDFMathTranslate-next · Web UI 设计审查报告

审查对象：webui/（index.html · styles.css · ui.css · app.js）· 方式：源码逐行审查 + 真实浏览器渲染实测 · 日期：2026-09-24

结论：有问题，但问题不在骨架上。

这套界面的底层是健康的 —— 设计令牌、8px 级距、明确定义的断点、一套完整的深色主题、用自定义对话框替换了原生 alert/confirm、图标走 SVG sprite 而非图标字体。判断力是在线的。

缺陷集中在三处必修：键盘焦点在全站不可见（四个开关完全没有焦点提示）、深色主题下开关开启态的旋钮消失（实测对比度 1.05:1）、「重试」按钮用了「加载中」图标。其余 18 项属于设计债、小屏细节与代码整洁度，不影响主流程，但不该留到发布之后。

一、必修缺陷

P0-1 键盘焦点在全站不可见，四个开关完全没有焦点提示

全局规则 ui.css:40 把浏览器默认的焦点环关掉了：

:focus { outline: none; }                                        /* ui.css:40 */
:focus-visible { box-shadow: 0 0 0 3px rgba(15, 23, 42, 0.12); } /* ui.css:41 */

替代方案是一个 12% 透明度的黑色阴影。浏览器内实测：button.matches(':focus-visible') 返回 true（规则确实生效了），但 12% 黑叠在白底上合成后约为 #e2e3e5，对比度只有 1.29:1，WCAG 2.4.11 要求不低于 3:1。输入框那条更弱 —— styles.css:253 用的是 6% 透明度，约 1.13:1。

更严重的是开关。四个开关的标记结构是 <span class="switch"><input type="checkbox"><span class="track"></span></span>，而 styles.css:327 把真实的 input 压成了零尺寸：

.switch input { position: absolute; opacity: 0; width: 0; height: 0; }  /* styles.css:327 */

浏览器实测该 checkbox 的渲染尺寸为 0 × 0 px。于是那圈 box-shadow 被画在一个零尺寸的盒子上 —— 用户按 Tab 移动到开关时，屏幕上不出现任何变化，无法判断焦点在哪儿。这是标准的 WCAG 2.4.7 失败。

建议改法

/* ui.css：替换第 40-41 行 */
:focus { outline: none; }
:focus-visible {
  outline: 2px solid var(--primary);
  outline-offset: 2px;
  box-shadow: none;
}
[data-theme="dark"] :focus-visible { outline-color: #f8fafc; }
.btn-primary:focus-visible,
.btn-destructive:focus-visible { outline-color: var(--text); }

/* 关键补充：把焦点画到可见的 track 上，而不是零尺寸的 input 上 */
.switch input:focus-visible + .track {
  outline: 2px solid var(--primary);
  outline-offset: 2px;
}
[data-theme="dark"] .switch input:focus-visible + .track { outline-color: #f8fafc; }

用 outline 而不是加粗 box-shadow 有两个好处：不受 border-radius 切割影响，也不会在按钮已经带阴影时被覆盖。

P0-2 深色主题下，开关开启态的旋钮消失（实测 1.05:1）

同一个 --primary 令牌被赋予了两种互相冲突的语义。主按钮在深色主题里需要反相成浅色，于是 ui.css:209 把 --primary 改成 #f8fafc；而开关的开启态 styles.css:350 正好也在用这个令牌：

.switch input:checked + .track { background: var(--primary); }  /* styles.css:350 */
.switch .track::after { background: #fff; ... }                 /* styles.css:345 */

[data-theme="dark"] { --primary: #f8fafc; }   /* ui.css:209 —— 为反相主按钮而改 */

结果：开关开启时轨道变成 #f8fafc，旋钮是 #fff，浏览器实测两者对比度 1.05:1 —— 视觉上是一块纯白胶囊，看不出旋钮位置。关态反而正常（深轨道配白钮），于是同一个组件在两种状态下的可读性完全不对等。

建议改法

/* styles.css :root 新增 */
--switch-on: #0f172a;

/* ui.css [data-theme="dark"] 内新增 */
--switch-on: #3b82f6;   /* 或 #cbd5e1，但必须与白色旋钮拉开对比 */

/* styles.css:350 改为 */
.switch input:checked + .track { background: var(--switch-on); }

同源问题还有一处：styles.css:299 的 .btn-primary:hover { opacity: 0.9 } 也是令牌不够用导致的取巧写法。深色主题下它会把白色主按钮压成灰白，主次按钮的层级反而变模糊。建议补一个 --primary-hover 令牌取代 opacity。

P0-3 「重试」按钮用的是「加载中」图标

app.js:795

actions += "<button class=\"icon-btn\" title=\"重试\" data-retry=\"" + task.id + "\">" + icon("i-loader") + "</button>";

i-loader 是那个八根辐条的旋转加载图标。失败任务旁出现一个「加载中」图标，语义完全相反 —— 用户会以为任务正在重跑。图标精灵里也确实没有任何刷新类图标（index.html:14-37 共 24 个 symbol，无 refresh / rotate）。

改法：在 sprite 里补一个 i-rotate-ccw，替换 icon("i-loader")；失败行同时建议补一个红色文字标签「重试」，纯图标按钮在长列表里的辨识成本偏高。

四、值得保留的部分

以下这些做对了，改的时候不要顺手推翻：

  • 令牌先行。颜色、圆角、状态色都收进了 :root，深色主题只做令牌覆盖而不重写组件 —— 这是唯一正确的做法，问题只在于覆盖位置放错了文件（见 P2）。
  • 主动接管焦点环的思路是对的。多数项目根本不会意识到需要接管，只是这里力度不够。
  • 桌面观感处理到位。ui.css 里禁文本选中、禁图片拖拽、自定义细窄滚动条、禁 overscroll 橡皮筋，配合壳层关掉 WebView2 的右键菜单和快捷键 —— 这套组合让 web 界面真的像原生窗口，是全项目最见功力的一段。
  • 用自定义对话框彻底替代了原生 alert/confirm，连 Esc 取消、Enter 确认、点遮罩关闭都做了。
  • 图标走 SVG sprite（24 个 symbol）而非图标字体，无闪烁、可控色、可缩放。
  • 响应式断点定义清晰（1100 / 720 两级，窄屏把侧栏改为横向导航条），只是移动端细节没调完。
  • 对比度整体过关。实测 19 项中 18 项 PASS，唯一不达标的 4.34:1 也已定位到背景色而非文字色。
